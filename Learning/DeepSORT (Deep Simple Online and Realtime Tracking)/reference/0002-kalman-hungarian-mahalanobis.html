Kalman Filter, Hungarian Algorithm, Mahalanobis Distance

The three mechanisms underneath both SORTTracker and DeepSORT — what each one actually computes, and where to find it in this codebase's KalmanBox.

Kalman filter

A recursive estimator: keeps a running belief about an object's state (position, velocity) and its own uncertainty about that belief, and updates both every frame in two steps.

SymbolMeaning
xState vector — the thing being estimated.
PState covariance — the filter's own uncertainty about x.
FTransition matrix — how state evolves one frame to the next, absent new information.
QProcess noise — how much unmodeled randomness enters the system per step (e.g. an object can accelerate, and the constant-velocity model doesn't know that).
zMeasurement — the new detection box.
HMeasurement matrix — maps state space down to measurement space (e.g. drops the velocity components, since a detection has no velocity reading).
RMeasurement noise — how much to distrust the detector itself.
KKalman gain — computed each step; decides how much to trust the new measurement versus the prior prediction.
Predict:
  x' = F x                (advance state by the motion model)
  P' = F P Fᵀ + Q         (uncertainty grows — motion model isn't perfect)

Correct (once a detection arrives):
  y  = z − H x'            (innovation: measurement minus predicted measurement)
  S  = H P' Hᵀ + R         (innovation covariance)
  K  = P' Hᵀ S⁻¹           (Kalman gain — how much to trust the measurement)
  x  = x' + K y            (blend prediction and measurement)
  P  = (I − K H) P'        (uncertainty shrinks — new information arrived)
Intuition on K: if R (measurement noise) is large relative to P' (state uncertainty), K is small — the filter barely moves toward the new detection, trusting its own prediction more. If P' is large relative to R — a track that hasn't been seen in a while, uncertainty ballooned — K is large, and the filter snaps close to the new measurement.

predict() (called every frame, even without a match) runs the top half of the algorithm above. update() (called only on a matched detection) runs the bottom half. An unmatched track still gets predict()-ed — its P keeps growing every frame it goes unseen, which is exactly the signal Mahalanobis gating (below) would use, and exactly why a long-unseen track's position estimate should be trusted less.

Hungarian algorithm (linear assignment)

The assignment problem: given an N×M cost matrix (rows = tracks, columns = detections), find the one-to-one pairing that minimizes total cost — optimal, not greedy. A greedy "take the best match first" approach can lock in a locally-good pair that blocks a much better global pairing later; the Hungarian algorithm (Kuhn, 1955) solves the whole matrix at once in polynomial time (O(n³)).

Worked intuition: tracks A, B and detections 1, 2. Cost(A,1)=1, Cost(A,2)=2, Cost(B,1)=2, Cost(B,2)=5. Greedy picks A↔1 first (cheapest cell, cost 1), forcing B↔2 (cost 5). Total: 6. Optimal is A↔2, B↔1: cost 2+2=4. The greedy pick looked best locally and was wrong globally — this is precisely the failure mode the algorithm exists to avoid.

SORTTracker calls this once per frame, across every track and every detection simultaneously. DeepSORT's matching cascade (see Reference 0001) calls it repeatedly — once per track-age bucket — instead of once globally.

Mahalanobis distance

A distance from a point to a distribution, measured in units of that distribution's own standard deviation along each direction — not raw Euclidean distance, which treats every direction as equally uncertain. 

d² = (x − μ)ᵀ Σ⁻¹ (x − μ)

  x : the point being measured (a detection, in tracking-space coordinates)
  μ : the distribution's mean (a track's predicted state)
  Σ : the distribution's covariance (the Kalman filter's predicted P, projected into
      measurement space — this is exactly S from the Kalman equations above)

Why Σ⁻¹ matters: a Kalman track's uncertainty is not a circle. A fast-moving object has wide uncertainty along its direction of travel (small errors in velocity estimate compound quickly) and tight uncertainty perpendicular to it. Squaring the raw offset and dividing by Euclidean distance ignores this shape entirely — Mahalanobis distance stretches the metric to match it: the same physical pixel offset counts as "close" along the uncertain axis, "far" along the confident one.

Raw IOU threshold (SORT)

One flat cutoff, applied identically to a track seen 1 frame ago and a track seen 10 frames ago — even though the second one's position estimate is far less trustworthy.

Mahalanobis gate (DeepSORT)

Threshold is on standard deviations, not pixels — a track that's been unseen longer has larger P (hence larger S), so the same pixel offset produces a smaller Mahalanobis distance and survives gating. The metric adapts to how much the filter currently trusts itself.

Not currently used in SORTTracker — only IOU. But the plumbing already exists: kalman_box.py:72 explicitly excludes "mahalanobis" from the set of keys saved from filterpy.common.Saver, meaning the attribute is present on self.kf (filterpy computes it internally for its own likelihood calculations) and simply unused downstream. Wiring gating into SORTTracker's matching step would tap directly into that.

Read together, these three: Kalman produces a state estimate and a covariance every frame; Mahalanobis turns that covariance into a distance-based gate for candidate matches; Hungarian takes whatever candidates survive gating and finds the globally optimal pairing. SORT uses only the first and third — DeepSORT's gating step is what's missing in between.
