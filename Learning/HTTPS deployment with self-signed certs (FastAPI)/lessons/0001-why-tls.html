Lesson 1

Why your security team said no to HTTP

The one idea underneath every TLS decision you'll make on real-time-manager-pipeline.

By the end of this lesson You can explain, in one sentence, what plain HTTP is missing and what TLS adds — using the words confidentiality, integrity, and authentication correctly.

What HTTP actually sends

Right now real-time-manager-pipeline serves http://0.0.0.0:8000. HTTP is just text over a TCP socket — no scrambling, no wrapper. Anyone who can see the network traffic (a router in between, a shared Wi-Fi, a compromised switch) can read every request and response byte-for-byte. Headers, API keys, JSON bodies — all in the clear.

client ──plaintext request──▶ server client ◀─plaintext response── server ↑ anyone on the path can read this, or edit it, undetected

That's the finding your security team is reacting to. Not "the app is insecure" in some vague sense — specifically: nothing stops an eavesdropper from reading traffic, and nothing stops a tamperer from changing it in flight.

What TLS adds

TLS (Transport Layer Security — the "S" in HTTPS) wraps that same TCP connection in a layer that gives you three properties:

1. Confidentiality

The client and server agree on a shared secret key (via asymmetric key exchange, then fast symmetric encryption for the actual data) so the payload is unreadable to anyone in the middle.

2. Integrity

Each message carries a cryptographic check. If a single bit is altered in transit, the receiver detects it and drops the connection instead of silently accepting corrupted data.

3. Authentication

This is the one that involves certificates. The server presents a certificate — a document containing its public key and identity claim (e.g. "I am manager.internal"), digitally signed by someone. The client checks that signature to decide whether to believe the identity claim.

This third property is where "self-signed" enters the picture — and it's the one your next lesson will dig into. Confidentiality and integrity work identically whether the cert is self-signed or CA-signed; only authentication trust differs.

Why this matters for your deployment

Today, docker-compose.yml exposes port 8000 over plain HTTP. Any client talking to it — including anything crossing a network segment you don't fully control — is exposed on all three properties above. Switching to HTTPS with a cert (self-signed, per your security team's instruction) fixes confidentiality and integrity outright, and gives you a form of authentication that's weaker than a public CA cert but still meaningfully better than nothing — more on that trade-off next lesson.
